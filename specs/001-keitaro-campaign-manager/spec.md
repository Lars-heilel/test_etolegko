# Feature Specification: Keitaro Campaign Manager

**Feature Branch**: `001-keitaro-campaign-manager`  
**Created**: 2026-11-14  
**Status**: Draft — обсуждается  
**Input**: Тестовое задание Adrobot: создание кампаний в Keitaro и редактор офферов существующей кампании.

## 1. Контекст и цель

Приложение закрывает два сценария работы с рекламным трекером Keitaro:

1. **Создаватор кампаний** — по названию, гео и офферу создаёт в Keitaro кампанию с двумя потоками: гео-редирект на Google и выбранный оффер.
2. **Редактор кампании** — открывает существующую кампанию и позволяет добавлять, удалять и возвращать офферы, показывая проценты ротации.

Приложение не выполняет редиректы и не подменяет Keitaro: оно только настраивает кампанию через API, а трафик обрабатывает сам трекер.

## 2. Scope

### Входит в scope

- Создание кампании: название, одна страна, оффер с поиском и выбором, кнопка «Создать».
- Поиск оффера в Keitaro для формы создания.
- Создание двух потоков:
  - поток 1 — фильтр по гео, редирект на Google;
  - поток 2 — выбранный оффер.
- Открытие существующей кампании Keitaro в редакторе.
- Ручное получение всех потоков кампании.
- Просмотр офферов и процентов ротации.
- Добавление оффера с пересчётом процентов.
- Удаление оффера с переводом в 0% и возможностью вернуть.
- Фиксация процентного соотношения.
- Сохранение изменений в Keitaro по кнопке.

### Не входит в scope

- Авторизация и роли.
- Статистика, конверсии, постбэки, лендинги, S2S.
- Создание и редактирование офферов, доменов, групп и источников.
- Клонирование кампаний и массовые операции.
- Несколько подключений Keitaro одновременно.
- Автоматическая синхронизация с Keitaro.

## 3. Пользовательские сценарии

### US-1. Создание кампании

1. Пользователь открывает форму создания.
2. Указывает название, выбирает одну страну, находит и выбирает оффер.
3. Нажимает «Создать».
4. Приложение создаёт в Keitaro кампанию с двумя потоками.
5. Пользователь видит результат и может открыть кампанию в редакторе.

### US-2. Редактирование офферов

1. Пользователь открывает существующую кампанию.
2. Нажимает «Получить потоки» — приложение загружает все потоки и офферы.
3. Потоки без офферов пропускаются и не разбираются.
4. Пользователь видит офферы и проценты ротации.
5. Добавляет оффер — проценты пересчитываются поровну между активными офферами.
6. Удаляет оффер — он переходит в 0% и отображается как удалённый.
7. При необходимости возвращает удалённый оффер кнопкой «Вернуть».
8. Нажимает «Сохранить» — изменения уходят в Keitaro.
9. Повторно нажимает «Получить потоки» — видит актуальное состояние из Keitaro.

## 4. Функциональные требования

### 4.1. Создание кампании

- **FR-001**: Форма принимает только название кампании, гео-код одной страны (ISO-2, выбор из списка) и оффер (автодополнение с поиском и выбором). Домен, группа и источник не требуются и не отображаются. Форма не запрашивает form-options.
- **FR-002**: Оффер выбирается через поиск по офферам Keitaro.
- **FR-003**: Домен, группа и источник выбираются из соответствующих списков Keitaro API.
- **FR-004**: Созданная кампания содержит два потока:
  - поток 1 — принимает трафик из указанного гео и редиректит на Google;
  - поток 2 — редиректит на выбранный оффер.
- **FR-005**: API принимает минимальный запрос `name`, `country_code`, `offer_id`. Необязательные legacy-поля `domain_id`, `group_id`, `traffic_source_id` передаются в Keitaro только если указаны; фиктивные ID не используются.
- **FR-006**: После создания пользователь видит, что кампания создана, и может перейти к её редактированию.

### 4.2. Получение данных кампании

- **FR-009**: Список кампаний для выбора подтягивается из Keitaro постранично. Поиск по названию выполняется по уже загруженному списку: в Admin API у `GET /campaigns` есть только `offset` и `limit`, параметра поиска нет.
- **FR-010**: Редактор открывает существующую кампанию Keitaro.
- **FR-011**: Потоки и офферы загружаются по кнопке «Получить потоки». Автоматической синхронизации нет.
- **FR-012**: Загружаются все потоки кампании.
- **FR-013**: Потоки, в которых нет офферов, пропускаются: их содержимое не разбирается и не отображается.

### 4.3. Редактор офферов

- **FR-020**: Редактор показывает офферы в потоках и их процентное соотношение.
- **FR-021**: Пользователь может добавить оффер через поиск.
- **FR-022**: При добавлении оффера проценты пересчитываются поровну между активными офферами: было 3 оффера — стало 4, у каждого по 25%.
- **FR-023**: Есть кнопка «Зафиксировать процентное соотношение». Вес зафиксированного оффера не меняется; пересчёт идёт только между остальными активными офферами. Удалённые офферы всегда 0%. Если зафиксированы все активные офферы, новый оффер получает 0%.
- **FR-024**: Удалить можно любой оффер. Удалённый оффер переводится в 0% и отображается как удалённый. Это локальное состояние: в Keitaro записи об удалённом оффере нет.
- **FR-025**: У удалённого оффера есть кнопка «Вернуть», которая встраивает его обратно в общий поток с пересчётом процентов.
- **FR-026**: Если оффер удалён на стороне Keitaro, после «Получить потоки» он отображается как удалённый и его можно вернуть.
- **FR-027**: Изменения применяются в Keitaro по кнопке «Сохранить». В Keitaro уходят только активные офферы; удалённые отсутствуют в потоке.
- **FR-028**: Ошибки Keitaro показываются пользователю понятным сообщением, без потери несохранённых изменений.
- **FR-029**: Один и тот же оффер нельзя добавить в поток дважды.

## 5. Принятые решения

- **Гео** — одна страна, простой select. Multi-select и строка через запятую отклонены.

## 6. Критерии успеха

- **SC-001**: Кампания создаётся по названию, одной стране и выбранному офферу даже при отсутствии доменов, групп и источников.
- **SC-002**: В созданной кампании ровно два потока: гео-редирект на Google и выбранный оффер.
- **SC-003**: По кнопке «Получить потоки» редактор показывает все потоки с офферами и пропускает потоки без офферов.
- **SC-004**: После добавления оффера проценты активных офферов пересчитаны поровну.
- **SC-005**: Удалённый оффер отображается с 0% и может быть возвращён.
- **SC-006**: После «Сохранить» и повторного «Получить потоки» состав офферов и проценты совпадают с Keitaro.
- **SC-007**: Пользователь понимает результат действий: успех, удалённое состояние, ошибка.

## 7. Стек и инженерные соглашения

### 7.1. Backend

- Python 3.12+, управление зависимостями — `uv`.
- FastAPI + Pydantic v2 (`pydantic-settings`), Uvicorn.
- SQLAlchemy 2.0 (async), PostgreSQL 16, `asyncpg`, Alembic.
- HTTP-клиент Keitaro — `httpx.AsyncClient`, таймауты, retry с backoff только на 5xx/сетевые ошибки.
- Тесты — `pytest`, `pytest-asyncio`, `respx`, `httpx.ASGITransport`.
- Линтеры — `ruff` (lint + format), `mypy`.
- Логи — структурные, обязательный `request_id`, без ключей и PII.

**Архитектура backend определяется исключительно skill `python-fastapi-ddd-skill`.** Спека не дублирует структуру слоёв, правила зависимостей, именование сущностей, use case, репозиториев и DI — они берутся из skill и выполняются буквально. Дополнительные конвенции — по `fastapi-patterns` и `sqlalchemy-alembic-expert-best-practices-code-review`. При расхождении спеки и skill по вопросам архитектуры приоритет у skill.

### 7.2. Frontend

- Vite + React 19 + TypeScript (strict).
- React Router 7, TanStack Query для серверного состояния, `fetch`-обёртка или `ky`.
- shadcn/ui + Tailwind CSS, `lucide-react`.
- `react-hook-form` + `zod` (`@hookform/resolvers`) для форм и валидации.

**Структура frontend определяется исключительно skill `feature-sliced-design`.** Спека не описывает слои, слайсы, правила импортов и публичные API — они берутся из skill и выполняются буквально. UI — по skill `shadcn`, роутинг — по skill `react-router`, производительность — по `vercel-react-best-practices`.

### 7.3. Общие соглашения

- API: REST, `/api/v1`, snake_case в JSON, ISO-8601 UTC.
- Ошибки: коды машинночитаемые (`VALIDATION_ERROR`, `KEITARO_UNAVAILABLE`, `CAMPAIGN_NOT_FOUND`, `VERSION_CONFLICT`, `OFFER_ALREADY_EXISTS`, `LAST_OFFER`).
- Секреты — только `.env`; в репозитории `.env.example`.
- Docker Compose: `postgres`, `backend`, `frontend` (dev). Прод-режим не требуется.
- Git: Conventional Commits, один PR = одна часть задания (creator/editor) + инфраструктура.
- README: запуск, миграции, переменные окружения, тесты, ограничения.

### 7.4. Обязательные skills

Перед написанием кода агент обязан загрузить и соблюдать:

- backend-архитектура: `python-fastapi-ddd-skill` — единственный источник истины по структуре backend;
- backend-практики: `fastapi`, `fastapi-patterns`, `sqlalchemy-alembic-expert-best-practices-code-review`;
- frontend-структура: `feature-sliced-design` — единственный источник истины по структуре frontend;
- frontend-практики: `shadcn`, `react-router`, `vercel-react-best-practices`;
- процесс: `test-driven-development`, `verification-before-completion`.

Писать код без загруженных и соблюдаемых профильных skills запрещено.
